# Research Agent 研究深度方案对比

日期：2026-05-03

本文记录 Eino 版 research agent 第一版可以选择的三种研究深度方案，并从实现复杂度、效果、测试难度、成本和后续扩展等角度做对比。

## 方案一：单轮搜索 + 总结

### 执行流程

1. CLI 接收用户问题。
2. 程序根据用户问题生成一个搜索查询。
3. 搜索 provider 返回前 N 条结果。
4. 模型接收用户问题和搜索摘要。
5. 程序输出 Markdown，或在传入 `--json` 时输出 JSON。

### 实现形态

- 更像一个确定性的 pipeline。
- 可以用 Eino 的基础 ChatModel 调用，或用一个简单的 compose chain。
- 模型不会自主决定何时调用工具。
- 搜索接口很简单，例如 `Search(ctx, query, limit)`。

### 优点

- 实现复杂度最低。
- 延迟和调用成本最低，通常只需要一次搜索和一次模型调用。
- 测试最容易，因为控制流稳定。
- 适合窄问题、事实查询和 CLI 的早期冒烟验证。

### 缺点

- 不够 agentic，本质是“搜索增强总结器”，不是模型自主驱动的 research agent。
- 查询质量决定上限。如果第一次查询写得不好，最终答案也会变弱。
- 不擅长自动扩展关键词、对比多个角度、补充缺失信息。
- 对市场分析、技术选型、竞品比较这类宽问题支持较弱。

### 适用场景

如果第一目标只是做一个最小可用的搜索辅助总结工具，可以选择该方案。

## 方案二：ReAct 多轮搜索 Agent

### 执行流程

1. CLI 接收用户问题。
2. 程序创建 Eino `ChatModelAgent`。
3. Agent 获得一个 `web_search` 工具，该工具底层可以接 Mock Search 或 Google Custom Search。
4. 模型自主决定是否调用 `web_search`、使用什么查询词、是否需要多次搜索。
5. 程序通过最大迭代次数、最大搜索次数、超时和返回结果数量来做边界控制。
6. 最终答案默认输出 Markdown，传入 `--json` 时输出 JSON。

### 实现形态

- 使用 Eino ADK 的 `ChatModelAgent` 作为核心 agent 抽象。
- 使用 Eino tool utilities 暴露类型化的 `web_search` 工具。
- 搜索 provider 逻辑与 Eino 工具包装分离，后续 HTTP 服务可以复用同一套 provider。
- 单独提供 Markdown 和 JSON renderer。
- 显式加载 OpenAI-compatible 模型配置和 Google Search 配置。

### 优点

- 更像真正的 research agent：模型能根据已有结果决定下一步查什么。
- 能在看到早期搜索结果后调整查询词。
- 能在实现成本、能力和测试复杂度之间取得比较好的平衡。
- 符合“基于 Eino 框架实现 agent”的目标，而不是只包装一次 LLM 调用。
- 后续可以自然演进到更深的研究模式，而不需要推倒 CLI、搜索 provider 和输出契约。

### 缺点

- 依赖支持 tool calling 的模型。
- 行为比方案一更不确定。
- 可能消耗更多 token 和搜索 API 配额，因为模型可能多次调用搜索工具。
- 需要明确 guardrails：最大迭代次数、最大搜索次数、超时、输出格式约束。
- 测试要更重视稳定边界，模型和搜索行为尽量通过 mock 控制。

### 适用场景

最适合作为第一版 Eino research agent。它能体现 agent/tool loop，同时复杂度仍可控。

## 方案三：Deep Research / Plan-Execute Agent

### 执行流程

1. CLI 接收用户问题。
2. Planner 先拆解子问题或研究任务。
3. 一个或多个 worker agent 独立搜索。
4. Synthesis 步骤去重、对比、检查来源覆盖，并生成最终报告。
5. 程序输出 Markdown 或 JSON，其中可以包含更丰富的查询轨迹、来源和中间发现。

### 实现形态

- 可以使用 Eino 更深入的 ADK 模式，或自定义 plan-execute workflow。
- 需要显式管理任务状态、中间发现、来源跟踪和聚合逻辑。
- 可能需要并发、重试、checkpoint 和进度事件。
- 输出契约要比第一版 CLI 更严格。

### 优点

- 对宽问题、开放式研究任务的答案质量潜力最高。
- 能从多个角度并行或分步搜索，覆盖面更好。
- 更适合加入来源评分、矛盾检查、按章节引用等高级能力。
- 长期来看，更接近严肃 research 产品的形态。

### 缺点

- 实现复杂度最高。
- 延迟和调用成本最高。
- 测试最困难，因为有多个模型驱动步骤，输出波动更大。
- 失败模式更多：计划拆错、重复搜索、聚合质量差、引用漂移、局部失败等。
- 对第一版 CLI 来说偏重，容易影响基础架构稳定性。

### 适用场景

适合作为后续增强方向。建议等基础 CLI、搜索 provider、输出契约和 ReAct agent 稳定后再做。

## 对比表

| 维度 | 方案一：单轮搜索 | 方案二：ReAct Agent | 方案三：Deep Research |
| --- | --- | --- | --- |
| Agent 行为 | 低 | 中高 | 高 |
| 实现复杂度 | 低 | 中 | 高 |
| 测试难度 | 低 | 中 | 高 |
| 延迟 | 低 | 中 | 高 |
| API 成本和搜索配额消耗 | 低 | 中 | 高 |
| 窄问题效果 | 好 | 好 | 好 |
| 宽问题效果 | 有限 | 好 | 最好 |
| Eino 使用深度 | 浅 | 较深 | 最深 |
| 第一版 CLI 适配度 | 可用但偏浅 | 最合适 | 偏重 |
| 后续 HTTP 扩展 | 容易 | 容易 | 容易，但需要更多状态管理 |

## 最终选择

第一版选择方案三：Deep Research / Plan-Execute Agent。

原因是该项目不仅要交付一个基础 research agent，也要帮助用户熟悉 Eino 框架在复杂场景中的实际使用。因此第一版会显式覆盖计划拆解、搜索执行、结果聚合和最终综合等更完整的 agent workflow。

设计时仍要控制范围：第一版应避免做多用户状态、长期记忆、复杂前端、数据库持久化和分布式任务队列。重点放在 CLI、Eino agent/workflow、搜索 provider 抽象、结构化输出和可测试的端到端流程。
